# DB95 case 12·39 원인 검수

상태: 실행 검증 및 최종 독립 QA PASS, GitHub 검수 브랜치 제출 승인. GATE=3/3, TABLE=10/10, 단독=2/2 PASS. 지정 목록은 PASS=7, FAIL=2, HOLD=1(실행 없음)이다. 릴리스 승인이 아니다. case 9·25·JS 묶음 HOLD, 장애 무결성 시험은 별도 단계다.

기준 DB95 HEAD c315ef23, FX HEAD a9ffce18. 기존 관련 변경사항과 미추적 자료를 보존했다. 지정 목록 10건 중 case 9는 실행 금지 지시를 우선하며 HOLD로 기록한다. TABLE은 원인 분류의 완성도이지 10/10 시험 PASS가 아니다.

## 공통 최소 수정과 원인

두 현상 모두 afj-tcp-row-map이 일반 map을 반환하는데 호출자가 atom처럼 deref한 결함에서 발생한다. 기존 src/tcp-server.fls의 afj-tcp-record-table-row-versions에서 deref 3곳을 제거한 수정만 사용했다. 이 회차에서 추가 제품 수정은 하지 않았다.

case 12: CREATE+INSERT batch는 record-row-versions-for-asts의 CREATE 분기에서 최종 행 집합의 최초 history를 기록한다. 기존 코드의 current는 map인데 deref current는 nil이므로 키 순회가 비어 최초 id=1 버전을 기록하지 못한다. lazy load는 빈 history를 복원하고 snapshot materialize는 begin revision의 버전을 조회하므로 최초 행을 볼 수 없다. 이번 수정 전 대조 실행 전용 저장 디렉터리에서 lazy_snapshot의 history에는 id=2·3만 있고 id=1이 빠진 것을 확인했다. alpha·beta history도 비어 있다. 이전 공유 임시 자료와 달리 이번 대조 실행에 귀속된 자료다.

case 39: UPDATE id=20→21 때 current를 nil로 잘못 읽어 변경되지 않은 id=15까지 삭제된 것으로 처리한다. close-row-version은 이미 기록된 deleted revision을 유지한다. 뒤의 실제 DELETE id=15에서 새 deleted revision이 생기지 않아 row-version-predicate-conflict?의 deleted > snapshot 조건이 성립하지 않는다. map을 직접 조회하면 UPDATE 때 살아 있는 id=15를 유지하고 실제 DELETE 때 버전을 닫는다. 이 세부 revision 경로는 소스에 근거한 설명이며 중간값을 직접 출력한 trace는 아니다. 공통 결함의 인과관계는 동일 런타임·동일 시험의 3곳 변경 대조로 확인했다.

## 대조 방법

기준 DB95 HEAD의 git archive를 별도 디렉터리에 펼쳤다. 원본 시험과 러너는 바꾸지 않았다. 기준 소스와 현재 소스의 제품 코드 차이는 위 deref 3곳뿐이다. case 12·39 대조에서는 동일한 현재 FX 런타임(기존 repeat 수정 포함), 동일한 Stage4, 원본 환경값과 120초 제한을 사용했다. 따라서 repeat 수정 유무가 비교를 혼동하지 않는다.

실행 전 ps 확인, flock -o /tmp/fl-heavy.lock, prlimit --as=2147483648 --core=0을 적용했다. 단계별로 다른 /tmp 저장 디렉터리를 바인드했다. 무거운 작업은 직렬화했고, case 9·25·JS 시험은 실행하지 않는다.

GATE의 case 7 실패 재현은 별도로 기준 DB95와 기준 FX runtime을 archive에서 읽어 수행했다. Stage0와 seed는 사용하지 않았고 기존 Stage4 실행 파일을 그대로 사용했다.

실행 명령: `bash tmp/DB95-next/run-review.sh baseline` 및 `bash tmp/DB95-next/run-review.sh subset`. 이는 원래 worker를 호출하는 임시 보조 스크립트이며 기존 러너 수정이 아니다. 단독 수정 후 12·39는 대조/목록 실행 전에 각각 한 번 실행했다.

검수 통과 조건부 GitHub 검수 브랜치 푸시만 허용되며 main 병합·배포·Forgejo 푸시는 하지 않는다. 두 관련 저장소의 검수 브랜치명은 review/db95-191-native-fixes다.

검수 조합의 FX commit은 fa7de514a759849527539914acab4cc131c81ba6이다. 이 DB95 변경의 subset 실행은 해당 commit과 동일한 runtime 소스로 수행됐다.

## 보존 및 증거

원본 release-gate/native-release-gate 러너와 case 12·39 원본 파일의 SHA 검사는 모두 OK다. 현재 두 저장소의 제품 코드 변경은 map deref 3곳과 기존 repeat 숫자 변환뿐이다. 기존 미추적 DB95-13 문서, case 9 대체 설계, 장애 시험 설계 및 tmp 자료는 검수 커밋 대상에서 제외하여 그대로 둔다.

실제 로그·결과·시각·3곳 patch·원본 SHA·보조 명령 사본을 docs/evidence/DB95-192에 보존했다. 출력 절대 경로만 가렸고 오류와 상태를 수정하지 않았다. 종료 후 이번 작업의 compiler·case-bin·daemon-bin·cc1·flock 잔류가 없으며 시작 전부터 있던 별도 bwrap은 건드리지 않았다.

기존 Stage4 실행 파일 SHA-256은 7bca2ea4c37619bce3f6047d88e9bace717129034c92836c322d2ba845cfdb2a다. 변경 runtime을 새 bootstrap으로 검증한 것은 아니다. 원래 worker의 -lcurl 링크는 기존 시스템 라이브러리를 가리키는 기존 임시 alias를 사용했으며 curl 설치·가짜 함수 추가는 없다.
