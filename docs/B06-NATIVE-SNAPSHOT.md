# B06 — 여러 변경을 저장할 때 전체 JSON 복제 제거

기존 DB 소스 `46d4abf65b8c7984e65526996d26cb269634231e`의 다중 AST 저장은 복구용 카탈로그·색인·데이터베이스 값을 보관하기 위해 전체 JSON 직렬화와 파싱을 반복했다. 단일 스레드의 실제 블로그 저장 함수를 100회 호출했으며 100/100 성공, 핸들러 총 26305ms였다. fsync 101회 합계는 0.004183초였다. 계측한 101회 복제에서 카탈로그 직렬화/파싱은 1493/2319ms, 색인은 3950/11341ms였다. 이 진단은 HTTP 인수 성능이 아니다.

수정은 FreeLang의 불변 map/vector 값을 기존 검증 경계 안에서 보관하는 것이다. 거부되면 보관한 정확한 이전 값을 복원한다. JSON 왕복 세 곳만 제거했으며 검증·잠금·WAL 형식/동기화·거절 시 WAL 무변경·복구 필요 상태는 바꾸지 않았다. 단일 테이블의 기존 경로도 그대로다. 새 API·언어·native 의존성은 없다.

고정 계약 20개는 `c888e8a2f55a26f2664c35067b23d89053d234f8`에서 구현 전에 커밋했고, 수정 전후 20/20이다. 최초 시험 커밋 `0e2d13ae99c7a08d30b95778143be00208498635`의 NULL 갱신 입력은 기존 구현이 거부하지 않아, 기대값·단언 20개를 유지하고 확실한 중복 기본키 거부 입력으로 준비를 바로잡았다. 이 원래 NULL 동작을 이번에 바꾸지 않았다. 원래 시험/정답/러너 변경은 0이다.

구현 소스는 `2b06e8783ad93b832255ebe5cee15e2eff08f7da`다. 이전 값 보존, 성공한 다중 변경, 중간 오류 뒤 카탈로그·색인·DB 복원, 거절 WAL 무변경, DDL 실패, 삭제 후 실패와 재시도 성공을 확인했다. 같은 진단 100회의 수정 후 핸들러는 6214ms, 실행 시간 29.20초/381924KiB였다. 수정 전은 50.42초/463336KiB였다. 초기 읽기까지 포함한 전체 시간과 핸들러 시간을 구분한다. 실제 HTTP 부하와 블로그 전체 회귀는 소비 저장소에서 별도로 인수한다.

검증은 고정 C seed에서 만든 승인 FX 컴파일러 SHA `62bf4232d41df948a3660e880eaa40082f48ac926ac16308c4d7790e34b91133`로 했다. 메모리 2147483648바이트/swap 0·공통 잠금을 지켰고 Node.js·TypeScript·Python을 실행하지 않았다. 단일 스레드 진단을 사용해 gprof의 스레드 샘플 해석을 피했다. 한 겹 strace의 syscall 요약은 별도이며 계측 빌드를 성능 인수에 사용하지 않는다.

[원문 목록](evidence/blog-b06-snapshot/SHA256SUMS)을 보존한다. 초기 AGENTS의 ‘메모리 기반 단계’ 문구와 달리 현재 소스에는 실제 WAL/트랜잭션이 존재하며, 여기서는 그 현행 소스와 실행 결과를 보고한다. 전체 DB 71건을 실행했다는 뜻은 아니며 확인한 범위는 명시한 20개 계약과 소비 앱 진단이다.
